## 阶段一：PRD 模板标准设计

### 1.1 需求背景

Billy 提出：要开发一个叫"在线工程师"的问答社区，希望先输出一份标准化 PRD 模板，满足以下目标：

- 让 AI 能很好地理解需求并进行开发
- 将 PRD 标准化，作为以后产品经理输出 PRD 的标准
- 开发人员可以通过 PRD 快速了解需求，并用于 spec coding

已有条件：
- 已经有非常细致的需求
- 已经使用 Axure 输出了高保真原型
- 还没有 PRD 文档
- 团队是正规团队（有专门的产品经理、前后端开发、测试等角色）

### 1.2 需求澄清

**Q1: 开发模式？**
- 问：你说的"用于 spec coding"，具体是指哪种开发模式？
- 答：开发者会根据 PRD 再进一步细化技术要求和开发细节，然后主要由 AI 开发，人工审核。
- 确认的工作流：PRD → 开发者细化技术方案 → AI 生成代码 → 人工审核

**Q2: 原型提供方式？**
- 答：可以提供截图/HTML

**Q3: PRD 语言？**
- 答：中文为主

**Q4: 文档格式？**
- 答：Markdown（.md）

**Q5: 团队规模？**
- 答：正规团队

**Q6: 当前痛点？**
- 答（全选 + 补充）：AI 难以解析、需求描述不清晰、逻辑/边界缺失、文档与原型脱节
- 补充：希望输出一份对开发人员和 AI 都友好的标准的专业的产品需求 PRD，固化为一个模板，PRD 一般应包含流程图、产品原型/demo，详细需求描述等

**Q7: PRD 组织方式？**
- 答：灵活拆分

**Q8: 原型呈现方式？**
- 答：截图 + 链接结合

**Q9: 流程图格式？**
- 答：Mermaid + 图片结合

**用户反馈**：在第 10 个问题时，Billy 表示"不要一直问我，结合你对 AI Coding 的理解，你来主导生成这个模板"。

### 1.3 方案对比

提出了 3 种 PRD 模板方案：

**方案 A：叙述式 PRD（传统风格）**
- 按章节线性叙述，从产品概述到功能细节一路写下来
- 优点：产品经理熟悉，上手成本低
- 缺点：AI 难以从大段文字中精确提取开发任务；边界条件容易被淹没在段落中

**方案 B：结构化 PRD（推荐 ✓）**
- 每个功能用固定结构描述：用户故事 → 验收标准 → 交互规则 → 边界/异常 → 数据对象 → 原型引用
- 优点：AI 可直接解析；开发者一目了然；边界条件有专门位置不会遗漏；模板强制产品经理思考完整
- 缺点：产品经理需要适应结构化写作，初期学习成本稍高

**方案 C：代码化 PRD（YAML/JSON Schema）**
- 用 YAML 或 JSON 定义功能的输入输出、状态机、API 契约
- 优点：AI 解析最友好
- 缺点：对产品经理极不友好；失去业务语境

**决定**：采用方案 B，在"人类可读"和"AI 可解析"之间取得最佳平衡。

### 1.4 模板整体结构设计

设计了 7 个部分 + 附录的 PRD 结构：

| 序号 | 章节 | 核心作用 | 谁写 | 谁读 |
|------|------|----------|------|------|
| 1 | 产品概述 | 说清楚是什么、为谁做、范围边界、外部依赖 | PM | 全员 |
| 2 | 术语表 | 统一业务领域语言和命名规范 | PM | 开发/AI |
| 3 | 用户角色与权限 | 定义角色及其能力边界 | PM | 开发/AI |
| 4 | 信息架构 | 页面/模块结构树 + 导航逻辑 | PM | 前端/AI |
| 5 | 功能模块（核心） | 逐个功能的结构化描述（占 70-80%） | PM | 开发/AI |
| 6 | 全局规则 | 跨功能的通用规则 | PM | 开发/AI |
| 7 | 非功能性需求 | 性能、安全、兼容性、无障碍等约束 | PM+技术 | 开发 |
| 附录A | 待确认事项 | 未确定问题追踪 | PM | 全员 |

设计原则：
- 第 1-4 部分是**上下文层**
- 第 5 部分是**主体层**
- 第 6-7 部分是**约束层**

### 1.5 功能模块模板（核心，10 个子节）

用户要求"尽可能细化，然后根据情况再进行适当裁剪"。

每个功能模块使用固定结构：

**5.x.1 功能概述** — 功能描述、用户故事、涉及角色、前置/后置条件、优先级、依赖功能、原型链接

**5.x.2 页面/界面描述** — 原型截图、页面状态（默认/空/加载/错误）、页面元素清单（编号 E-xx，页面内唯一）、布局说明
- 交互行为标准描述：提交表单、跳转到[页面]、打开弹窗、切换状态、筛选列表、展开/收起、上传文件、复制到剪贴板、显示loading

**5.x.3 交互逻辑** — Mermaid 主流程图、子流程/分支流程、页面跳转关系表

**5.x.4 业务规则** — 编号 BR-{功能编号}-{序号}，每条独立可验证

**5.x.5 边界与异常处理** — 编号 EX-{功能编号}-{序号}，含场景/触发条件/系统行为/用户提示/恢复方式

**5.x.6 数据对象** — 实体字段定义 + Mermaid ER 图（业务层面，非数据库设计）
- 类型可选：string, integer, float, boolean, datetime, enum, richtext, file, image, ref:{Entity}, string[], ref:{Entity}[]

**5.x.7 状态机（如有）** — Mermaid 状态图 + 状态转换规则表

**5.x.8 通知/消息触发** — 触发事件/接收人/通知方式/内容模板/延迟

**5.x.9 验收标准** — Given-When-Then 格式，编号 AC-{功能编号}-{序号}，分正常/异常/边界三类

**5.x.10 API 契约（可选）** — 接口/方法/路径/参数/返回
