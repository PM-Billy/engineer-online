## 你需要输出

### 1. 工程骨架

要求：
- 严格按目标任务的技术栈初始化，禁止自行替换框架
- 只创建当前任务需要的基础目录、依赖和配置，不提前生成无关业务页面
- 若任务是前端脚手架，需预留 i18n、Design Token、网络层、路由层接入点
- 若任务是后端脚手架，需预留 controller / service / repository / config / common / integration 包结构
- 若任务是本地基础设施任务，需给出最小可运行的容器编排与 healthcheck

### 2. 关键配置文件

要求：
- 前端：依赖清单、构建配置、路由 / 状态管理 / 请求层初始化
- 后端：`pom.xml` / `application.yml` / profile 结构 / actuator / OpenAPI 或 Swagger 基础配置
- 容器：`docker-compose.yml` / `.env.example` / 健康检查 / 端口分配
- 所有环境变量采用占位值或示例值，禁止写入真实密钥

### 3. 目录结构说明

要求：
- 用简洁列表说明你创建了哪些目录/文件，以及它们分别承载什么职责
- 若你对目录结构做了推断，必须说明推断依据来自哪份文档

### 4. 本地验证方式

要求：
- 说明如何启动、如何验证工程骨架可运行
- 若当前回合不实际运行命令，也要写出建议验证步骤

## 严格约束

| 项 | 规则 |
|---|------|
| **技术栈** | 以 `standard/技术架构.md` 为准，禁止自行升级/替换核心框架 |
| **范围控制** | 只做脚手架与基础配置；未进入对应业务任务前，不生成完整业务页面/接口 |
| **环境变量** | 使用示例值；真实密钥、域名、证书路径一律留占位 |
| **前端多语言** | 若脚手架涉及 UI 层，必须预留 `zh-CN` / `en-US` / `th-TH`（后台除外，仅 `zh-CN` / `en-US`） |
| **Design Token** | 前端脚手架需预留统一 Token 接入点，禁止后续页面直接硬编码颜色/字号 |
| **可运行性** | 输出必须能支撑“工程可启动 / 热更新 / 健康检查”这一类验收目标 |
| **补充假设** | 若任务清单未指定目录名、端口、包名，可做保守假设，但必须在结果中显式列出 |
